# 项目机制：已知语义与待确认项

设计来源：[卡牌设计 v0.1](../../../../docs/design/卡牌设计v0.1.md)。
实现状态：[status.md](../../../../docs/development/status.md)。

## 气：已实现基础版本

0 费、状态牌、抽 1（升级后 2）张、消耗。使用普通抽牌，允许游戏洗牌。
当前实现见[Qi](../../../../HeavySilentCode/Cards/Qi.cs)。生成气、把牌变化为气、检查是否有气等联动尚未实现。
临时加入战斗的气与永久加入套牌的气不是同一种操作，相关卡牌实现时必须明确范围。

## 磨顶 X：仅有设计，尚未实现

已知规则：把抽牌堆顶 X 张移入弃牌堆；不足 X 张时不执行磨顶及其后续操作。
不能把普通弃牌命令直接认定为磨顶，因为弃牌触发、牌堆来源和失败语义需要单独确认。

| 问题 | 为什么影响实现 |
| --- | --- |
| “后续操作”是本次关联效果，还是整张卡剩余效果？ | 决定多段卡和“伤害—磨顶—治疗”的控制流 |
| 不足时是否仍支付出牌费用？ | 设计的是使用门槛还是结算失败，影响不同接口 |
| 一次磨顶按一次操作还是逐张触发？ | 影响本回合次数和每当磨顶的监听 |
| 磨顶 0 是否成功并触发？ | X 费牌、空抽牌堆和递归效果的边界 |
| 磨顶是否触发原版弃牌效果？ | 牌堆移动与 Discard 并不等价 |
| 先批量移完，再自动打出，还是边移边打？ | 自动出牌可能抽牌、洗牌或改变待移动对象 |
| 被磨顶的攻击自动选择谁？ | 目标与随机数需要由游戏流程处理 |
| 自动重复打出的终止条件是什么？ | 避免无限递归与死亡目标继续结算 |

实现时需要使用一次操作的结果关联“其中的牌”，不能在后续步骤重新扫描整个弃牌堆冒充本次磨顶结果。

## 征召 X：仅有设计，尚未实现

已知规则：从抽牌堆顶抽 X 张；不足时抽入剩余牌，不洗牌。
本机原版 `CardPileCmd.Draw` 在需要时会洗牌，因此不能直接调用它并宣称征召成立。

实现前确认：

- 是否触发所有普通“抽到卡牌”效果，以及与不能抽牌的状态怎样交互。
- 手牌满时按原版抽牌限制处理，还是有其他行为。
- 抽牌触发造成牌堆变化时，针对开始时的快照还是逐张读取。
- 是否允许本次征召以外的触发效果自行洗牌。

## 后续复杂内容

奖励阶段改牌、获得卡牌时移除卡牌、替代费用支付、复制整个抽牌堆、跨回合费用与回合末返回牌顶，均需要额外核对生命周期。
“造成伤害”是计算伤害、扣除格挡后的实际生命损失还是多段累计，也需在相关卡牌开发时明确。
涉及“卡组中所有状态牌”时需区分永久 Deck 与战斗各牌堆。

这些问题不阻塞初始化。Agent 在开始对应机制时提出具体候选语义和影响，确认后才固化为代码、测试和本文规则。
