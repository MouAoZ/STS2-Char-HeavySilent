# 内容填充教程

核验基线：[baseline.json](../../../../docs/development/baseline.json)。
人类填写设计，Agent 完成代码、本地化、资源与验证。“填充”不要求人类编程，也不表示游戏能直接读取策划 Markdown。

设计按[三类正文](../../../../docs/design/README.md)分别维护：术语及共用规则进入[特殊机制设计](../../../../docs/design/mechanics.md)，所有卡牌进入[卡牌设计](../../../../docs/design/cards.md)，其他内容进入[遗物／事件／药水设计](../../../../docs/design/relics-events-potions.md)。技术教程引用这些规则，不另存副本。

## 如何判断工作量

| 内容 | 常规填充 | 需要新增程序能力 |
| --- | --- | --- |
| 卡牌 | 已有伤害、格挡、抽牌、加牌、施加状态的组合 | 磨顶／征召、新计数体系、改写费用支付、奖励阶段干预 |
| 遗物 | 已有触发时机上的常规效果 | 新触发时机、跨阶段状态、复杂保存或新 UI |
| 药水 | 已有使用流程、目标与即时效果 | 新目标交互、持续控制机制、特殊使用限制 |
| 事件 | 常规页面、选项、选牌、奖励与代价 | 新交互界面、特殊战斗流程、跨事件状态机 |

常规填充通常也会增加一个 C# 类型，但不会发明新的共用机制。需求是否“新机制”，取决于现有接口能否准确表达语义，而不是文字看起来是否简短。

## 填充一张卡：以气为例

1. 在[卡牌模板](../../../../docs/design/templates/card.md)填写：0 费、状态、无目标、抽一张、消耗，升级后抽两张。
2. Agent 分配 `HS-TOKEN-001` 与稳定 ID `HEAVYSILENT_QI`，建立[Qi](../../../../mod/HeavySilentCode/Cards/Qi.cs)。
3. 从 `HeavySilentCard` 继承；费用和类型由构造参数给出，抽牌量由 `CardsVar` 给出，消耗由关键词给出。
4. `OnPlay` 等待原版抽牌命令；`OnUpgrade` 增加抽牌量。
5. 在 eng／zhs 的 `cards.json` 增加 `.title`、`.description`，描述使用 `{Cards:diff()}`。
6. 继承基类上的 Pool 注册，暂用基类的占位图；正式卡图准备好后，为这张卡显式覆盖图片路径。
7. 执行 `verify`、`package`，并验证足量牌、空牌堆、手牌上限和升级情形。
8. 更新[卡牌设计](../../../../docs/design/cards.md)的状态、模型 ID 和代码链接，以及[设计跟踪](../../../../docs/design/implementation-tracker.md)的汇总；同步 README 看板与状态页验证证据，提交可供人类 Review 的行为说明，新增的教学解释另写入样例文档。

改“抽 1／2 张”为其他数值时，主要修改 `CanonicalVars` 的基础值和 `OnUpgrade` 的差值。
改“抽牌”为“征召”则改变了机制，不能只改描述，也不能直接给普通抽牌命令换个中文名字。

## 填充遗物

使用[遗物模板](../../../../docs/design/templates/relic.md)，优先明确“何时触发”和“何时重置”。
Agent 查阅当前版 `RelicModel`／BaseLib 的 `CustomRelicModel`，为类指定本角色遗物池、稀有度、图标和本地化。
例如“每场战斗开始获得格挡”可复用已有战斗开始 Hook，再调用格挡命令；“本局累计三次满足条件后触发”则需要明确计数保存与重置。

新增遗物不会因文件放进 `Relics` 文件夹就自动拥有正确归属，需要实际 Pool 注册。
临时战斗计数不能误存为跨局静态变量；应保存的字段要按目标版本的序列化机制处理，并测试继续游戏。

## 填充药水

使用[药水模板](../../../../docs/design/templates/potion.md)。写清战斗内外是否可用、目标类别、无目标时能否使用、选择可否取消。
Agent 查阅 `PotionModel`／`CustomPotionModel` 的当前实现，沿用原版使用与消耗流程，在效果方法中组合命令。
药水图、轮廓图和文本都要提供；不要为了立即实现效果绕过游戏的玩家选择上下文。

验证至少包含正常使用、不合法目标、取消选择和效果触发后药水是否正确消耗。数值受哪些其他效果影响，由设计明确，再核对合适的命令参数。

## 填充事件

使用[事件模板](../../../../docs/design/templates/event.md)，以页面和选项表描述流程。
Agent 查阅 `EventModel`／`CustomEventModel`，实现出现条件、页面文本、可选条件、代价、结果和结束状态，再接入合适事件池或出现入口。
事件不像卡牌那样仅有一次 `OnPlay`，它通常跨越多个选择步骤。

“付费移除一张牌”需要确定先付费还是先选牌、能否取消、没有可移除牌时选项怎样显示。
如果已有页面和选择接口能够表达，就是常规填充；需要新的小游戏界面或跨房间追踪，则另做机制开发。

## 新机制的交付顺序

先列出精确规则和验收例子，再核对现有原版实现；将机制放入共享入口，由卡牌或遗物调用。
接口要能表达调用者真正需要的信息，例如磨顶是否成功、实际移动的卡牌、后续效果是否应继续；这些字段在语义确定前不提前固定。

首次实现机制时补充有意义的边界测试。普通数值填充以分析器、内容检查和适用的实机验证为主，不为每个常量写一套重复测试。

可见术语还需按[特殊机制设计](../../../../docs/design/mechanics.md#范围与交付)完成双语解释和悬停显示，将结算验证与提示显示验证分别记录。

## 内容资产与文案

所有资源使用 `res://HeavySilent/` 前缀，文本有 eng 和 zhs 两份；基础英文可先直译，但不能缺键。
卡牌数值用动态变量，图像路径大小写保持一致。新资源导入后执行 `package`，只运行 `build` 不会刷新已安装的 PCK。
卡牌、遗物、药水和事件的具体成员签名可能随 public-beta 改变；没有实际新增该类型前，不维护未经编译的“万能空壳代码”。
