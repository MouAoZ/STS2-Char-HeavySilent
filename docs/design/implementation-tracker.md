## 状态与编号约定

| 状态 | 含义 | 应有记录 |
| --- | --- | --- |
| 未实现 | 尚无符合当前设计的实现；有相似命令、占位卡或机制参考也不算已实现 | 设计、依赖与协作问题链接；无代码填“—”，待调整的旧代码保留链接并注明差异 |
| 进行中 | 已实际开工，代码或配套内容尚未完成 | 已有代码／工作分支、剩余工作；README 看板同步移入进行中 |
| 已实现 | 当前条目的效果、升级、注册和必要本地化已落地，相关源码／构建检查通过 | 稳定模型 ID、真实源码链接；实机结果单独记录 |

“已实现”不代表已通过完整爬塔、平衡或联机验收。具体内容登记稳定模型 ID 和代码；共用机制登记共享实现及术语接入位置，涉及悬停提示时必须同时完成规则和术语显示。当前三张已实现卡有[历史基础实机记录](../development/status.md#验证记录)，其余设计尚未实现。

- 已有设计编号保持不变；名称、顺序、稀有度与文档归属调整均不重编号、不复用撤销项编号。
- 设计编号与游戏模型 ID 是两回事。尚无实现的条目不预分配游戏模型 ID、不建立占位源码；保留旧代码的待调整项注明差异。
- `HS-MECH` 为特殊机制；`HS-BASE`／`HS-START` 为基础与特殊初始牌；`HS-TOKEN` 当前用于气；`HS-ATK`／`HS-SKL`／`HS-POW` 为角色攻击／技能／能力牌；`HS-ANCIENT` 为先古卡；`HS-RELIC` 为遗物。
- 尚无具体设计的诅咒、其他特殊奖励卡、事件与药水不建立空条目、不计入分母。首项设计确定时再分配相应编号。

## 日常维护

1. 按[设计入口](README.md)选择所属文档，直接维护对应条目的设计和状态；未解决的疑问与回答写入[协作文档](../collaboration/README.md)，设计条目只引用编号。初始卡组、事件和遗物通过编号引用相关卡牌，公共规则只在特殊机制文档维护；原始混合草稿仅作历史资料。
2. 移动条目保留编号；新增使用该系列的下一个未用编号；撤销条目保留编号与原因，移出当前统计。
3. 实际开工后，将所属设计文档的条目标为“进行中”，登记已有代码和剩余工作，并同步 [README 看板](../../README.md#开发看板)。仅排期或讨论仍为“未实现”。
4. 完成后登记实际模型 ID、源码与验证结果。代码位置使用文件链接；涉及术语的机制单列结算和悬停提示验证。实机证据写入[状态页](../development/status.md)，没有测试就明确写未验证。
5. 同次交付刷新本页统计、README 汇总与看板。设计变更使代码不再符合条目时，退回“进行中”（已着手调整）或“未实现”（待调整），保留旧代码链接和差异说明。
6. Skill 维护设计文档索引与技术工作流，玩法规则直接链接设计正文。发生冲突时回到原条目核对，不在 Skill 内另存规则副本。
7. 当前手动维护，没有自动同步。提交前核对编号唯一性、分类计数、设计覆盖与源码链接，运行 `python scripts/verify.py`；该命令检查本地链接、内容 ID 和本地化，不检查设计语义一致性。
8. 收到评论或 Review 后，按[处理约定](../collaboration/README.md#工作流)在原 Issue／PR 下继续讨论、更新正式文档与看板；同一问题必要时重开。完成后在同次交付中关闭并归档，分别记录设计决策、实现状态、评审结论和实际整合结果。
