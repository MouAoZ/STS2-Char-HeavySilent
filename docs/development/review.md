# 人类 Review 指引

先检查玩法与实际行为，再看实现是否容易维护。Agent 应提供以下材料，而不是要求人类从全部 diff 中自行猜测意图。

## 在哪里提出与回答

具体 Review 请求统一登记到[协作文档](../collaboration.md)，使用 R 编号并链接已交付的提交或文件。人类直接在 A 栏填写“通过／需要修改／暂缓”和意见，也可在 CLI 按编号回复；Agent 负责记录来源、处理修改并更新状态。格式与流转见[协作约定](../collaboration.md#状态与维护)。

设计待澄清属于决定“应该怎样做”，使用 Q 编号；Review 检查已交付的结果。两类都进入 [README 人类看板](../../README.md#人类协作看板)，确认后的规则写回设计。没有人类结论时，不把构建或自动测试通过标为人类 Review 通过；也不为已经授权的实现、验证或本地提交额外增加等待环节。

## 一次交付应说明

1. 对应哪个设计编号，玩家会看到什么变化。
2. 复用了哪些游戏命令，新增了什么项目机制。
3. 哪些源码入口值得阅读，以及关键语句的中文解释。
4. 验证了哪些情形，结果是什么；编译与实机分开报告。
5. 尚未确定的规则、临时占位、可能影响旧存档的变动；需要继续沟通的内容链接对应 Q／R 条目。

## 看卡牌时重点检查

- 费用、目标、升级、关键词是否与设计一致。
- 操作是否按文案顺序执行；失败是否只跳过应跳过的部分。
- 数值是否通过 DynamicVar 与描述共用；没有在文案中重复写死可变数值。
- 伤害、格挡、抽牌和移动是否使用合适的游戏命令。
- 状态属于哪个玩家、卡牌实例、回合或战斗，何时重置。
- 自动打出、复制、奖励修改等特殊情况是否有明确测试。

## 文档随改动更新

内容变更更新[所属设计文档](../design/README.md)的条目、状态、模型 ID 与代码链接，再同步[设计跟踪](../design/implementation-tracker.md)汇总和 [README 看板](../../README.md#项目进度)；验证结果写入[状态页](status.md)。共用规则直接更新[特殊机制设计](../design/mechanics.md)，涉及术语时分别验收结算和悬停解释；API 或版本变更更新原理、基线与升级说明。
只修正文案拼写时更新相关文本即可，不要求重写所有文档。

交接信息应落在仓库中：尚未解决的问题、回答与评审结论进[协作文档](../collaboration.md)，确认过的玩法和设计到代码的关系进所属设计文档，共用规则只在特殊机制设计维护，整体进度进 README，验证结论和未测范围进状态页。Skill 索引设计正文与协作入口；条目编号与维护步骤见[跟踪约定](../design/implementation-tracker.md#日常维护)。原始日志、存档和机器路径保留在忽略目录；换机器时缺少这些证据应明确说明，不能当作已复现。
按任务完成相关验证后创建本地 Git commit，交付提交号；提交前核对差异，不夹带本机配置或测试存档。

卡名可改，稳定模型 ID 不随意改；ID 会进入存档，修改它需要单独说明兼容策略。
引入 Harmony 补丁时，Review 材料须包含被补丁的方法、已有扩展入口不足的原因、版本和影响范围。
